## Overview

Discovery runs are how you trigger Atlas's source discovery workflow through the
API. You provide a location and issue areas, and Atlas searches public sources,
extracts candidate civic actors, attaches evidence, and produces reviewable
results.

This guide covers two common patterns:

- Start and inspect a hosted Atlas discovery run.
- Run Scout locally, sync selected results to Atlas, and open the resulting
  workspace run.

<Note>
  Discovery runs require authentication and an Atlas Pro or Team plan. See
  [authentication](/api-reference/authentication).
</Note>

## Start a discovery run

```bash
POST /api/discovery-runs
```

Discovery runs are **asynchronous**. The API returns `202 Accepted` immediately
with a run ID, then the pipeline executes in the background.

<CodeGroup>

```bash cURL
curl -X POST https://atlas.rebuildingus.org/api/discovery-runs \
  -H "X-API-Key: your-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "location": "Kansas City, MO",
    "issue_areas": ["housing_affordability", "union_organizing"]
  }'
```

```python Python
import httpx

response = httpx.post(
    "https://atlas.rebuildingus.org/api/discovery-runs",
    headers={"X-API-Key": "your-api-key"},
    json={
        "location": "Kansas City, MO",
        "issue_areas": ["housing_affordability", "union_organizing"],
    },
)

run = response.json()["data"]
print(f"Run started: {run['id']} — status: {run['status']}")
```

</CodeGroup>

**Response (202 Accepted):**

```json
{
  "data": {
    "id": "run-abc123",
    "location_query": "Kansas City, MO",
    "issue_areas": ["housing_affordability", "union_organizing"],
    "status": "pending",
    "started_at": "2026-04-22T15:00:00Z",
    "completed_at": null,
    "entries_found": 0,
    "sources_processed": 0
  }
}
```

## Check run status

```bash
GET /api/discovery-runs/{run_id}
```

Poll this endpoint to check progress:

```bash
curl -H "X-API-Key: your-api-key" \
  https://atlas.rebuildingus.org/api/discovery-runs/run-abc123
```

**Run statuses:**

| Status      | Meaning                        |
| ----------- | ------------------------------ |
| `pending`   | Run created, waiting to start  |
| `running`   | Pipeline is executing          |
| `completed` | Pipeline finished successfully |
| `failed`    | Pipeline encountered an error  |

When `status` is `completed`, `entries_found` and `sources_processed` show the results.

## Inspect before using results

Completion means the run finished, not that every result is ready for outreach,
publication, funding review, or import.

After a run completes, review:

- Which entries are people, organizations, initiatives, campaigns, or events.
- Which sources support each entry.
- Whether source dates are recent enough.
- Whether the same actor appears in multiple independent sources.
- Which issue areas are well-covered and which remain thin.
- Which records should stay private to a workspace until reviewed.

## Polling pattern

A simple polling loop to wait for completion:

```python
import httpx
import time

client = httpx.Client(
    base_url="https://atlas.rebuildingus.org/api",
    headers={"X-API-Key": "your-api-key"},
)

# Start the run
run = client.post("/discovery-runs", json={
    "location": "Kansas City, MO",
    "issue_areas": ["housing_affordability"],
}).json()["data"]

# Poll until done
while run["status"] in ("pending", "running"):
    time.sleep(10)
    run = client.get(f"/discovery-runs/{run['id']}").json()["data"]
    print(f"Status: {run['status']}")

print(f"Done! Found {run['entries_found']} entries from {run['sources_processed']} sources.")
```

## Run Scout locally and sync to Atlas

Scout is useful when you want a local, inspectable research process before
syncing selected results into Atlas.

The safe workflow is:

<Steps>

<Step title="Run Scout locally">
  Run the Scout CLI for the place and issue set. Keep the local artifact so the
  team can review source evidence before syncing.
</Step>

<Step title="Decide visibility">
  Separate entries that are ready for the public directory from entries that
  should stay private to a workspace. A weak, stale, or sensitive record should
  not become public just because Scout found it.
</Step>

<Step title="Sync the artifact">
Use the Scout sync endpoint:

```bash
POST /api/discovery-runs/syncs
```

The sync response includes the remote Atlas run id, entry visibility receipts,
and links that can open the synced run in the workspace.

</Step>

<Step title="Open the workspace run">
Open `/discovery?run=<remote_run_id>` to inspect the synced run in Atlas. Link
reviewed results to a brief, coverage target, or workspace list.
</Step>

</Steps>

## What sync receipts are for

Sync receipts make the boundary between local discovery, workspace data, and
public directory records explicit.

Look for:

| Receipt field   | Why it matters                                                                |
| --------------- | ----------------------------------------------------------------------------- |
| Remote run id   | Lets Scout and Atlas refer to the same synced run.                            |
| Entry links     | Connects local Scout entries to Atlas entries created or matched during sync. |
| Visibility      | Shows whether an entry is public, private, skipped, or needs review.          |
| Workspace links | Gives users a direct path back to the run, brief, list, or coverage target.   |

Read [Workspace endpoints and visibility](/api-reference/guides/workspace) for
more detail on `entry_links` and safe workspace usage.
